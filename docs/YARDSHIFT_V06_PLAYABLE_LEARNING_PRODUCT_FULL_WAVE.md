## 0. 完成定义：从“会点任务”到“有证据地学会判断”

### 北极星不变

玩家在**同一座庭院**中发现问题，先观察环境，判断安全前置和可选择顺序，挑选工具、实施操作、看到永久/暂时/重复劳动等后果，复盘真实行为，并在同条件第二次尝试中改善自己的决策。**不是**为通关而点击六个子关卡，不是强制背标准答案，不是装备收集，也不是将画面漂亮误认为教学成功。

### 预期学习产出（L0/L1）

| 能力 | 玩家完成后能独立回答或展示 | 必须由哪个可见行为支撑 | 反例（不算学会） |
|---|---|---|---|
| 观察/安全 | 为什么先检查石头或硬木？哪些工作可以自由调序？ | 检查实际改变局部风险信息；未清风险影响对应工具、清除后恢复 | 只是按“Inspect”后自动全院解锁 |
| 工具适配 | 为什么开阔草坪选宽割幅机，近花坛或边缘需更精确？ | 真实覆盖轨迹、误伤风险、边缘独立状态、电量/准备投入 | 工具只是换名字、每次点一下进度加相同数 |
| 操作差异 | 为什么线割不是拔根；为什么吹叶不等于装袋？ | 地上部分/根部状态分离、散→堆→袋状态演进 | 文本说不同，实际上同样一键清除 |
| 工序判断 | 为什么先清某地、再修篱可能造成二次工作？ | 同坐标剪枝掉落 → 再脏 → 第二次**实际**清理才计 rework | 不问地点仅按“错误顺序”扣分 |
| 复盘/迁移 | 同样条件下第二轮改什么，是否保安全和质量？ | 两次封存、可公平比较的终点质量/投入、事件证据 | 只是显示两个总分或命令用户按标准顺序重玩 |

**最终产品性验收必须由人类试玩证明**，而工程代理只能交付可验证的环境、行为证据及观察表。不要用 `112 tests passed` 直接给“已学会”盖章。

### 明确的范围上限

本轮优先把原本 F01–F09 的完整体验做实。**不**加入多人/社区、额外庭院、金币经济、完整人物骨骼、长期天气模拟、季节生长、语音讲师、开源大重构、真实品牌型号、动态 AI 对话；除非上述核心学习目标无法用现有轻量机制达成。允许小型视觉/交互改善，但必须解释它改善了哪项可理解性。

## 2. 整个玩家旅程的产品与实现合同（F01–F09）

**通用四拍：** (1) 玩家先看到“当前条件”；(2) 在合理选项中主动选工具/工序；(3) 真实操作产生可见世界变化与客观代价；(4) 轻量回顾解释现象，而不是开场就灌输答案。做错允许继续，安全危险除外；不强迫唯一专家顺序。

### F01 进入与现场观察：把“看见风险”变成实际价值

- **首次画面：** 一座有正常草坪、绿篱、花坛、路径、落叶、可辨识障碍物的完整庭院；保留 `SaturdayGardenModel.tsx` 与实际 glb。尽量在首 10 秒内看出至少三种可做的事；若热点覆盖/遮挡严重，优先调整 UI 标签/相机，不重新造院子。
- **操作：** 可以自由探索或按 Inspect；检查不是一键完成任务，也不是必须按固定顺序才能开始。检查后指出已观察到的**具体区域风险**（例如石头对应割草、硬木对应动力剪），而非只是 `inspection["garden-overview"] = true`。
- **代码定位：** `GardenShell.tsx`、`GardenHotspots.tsx`、`HazardTaskStage.tsx`、`gardenTasks.ts`、`gameStore.inspectObject`、`GardenDomain.inspection`、`GardenOverviewScene.tsx`。检查当前数据是否存在对区域/物件 ID 的一致映射（`task.id` vs `garden-overview`），只做薄映射，保留可探索性。
- **可见反馈：** 玩家可以理解“我检查了什么、发现了什么、下一步为什么需要留意”，不必读长教程。对尚未发现的风险给出轻量探索线索，不直接露出正确施工顺序。
- **验收：** 同一物件重复 Inspect 不重复扣 setup；检查前后知识信息不同；不检查也能自由做非危险工作；有风险局部阻断并能通过清除恢复。

### F02 工作计划与工具准备：不要把选择伪装成默认

- **流程：** 点击区域 → 出现该区实际问题、工具候选（名称+可辨图标/模型）、不同用途与局限、可自行选的工具；玩家必须做一次明显的选择操作，但无须填写问卷。重新访问同类任务可以合理保留最近选择以减操作成本，同时让用户看到这是记忆值不是系统推荐。
- **信息展示：** 优先回答“这一块现场有什么条件？”而不是直接写“这就是最佳选择”。让玩家知道机具电量、宽度/精度、花卉邻近、硬木阻挡等影响，并可返回总览更改计划。
- **代码定位：** `WorkConfirm.tsx`、`GardenShell.tsx`、`WorkPlanPanel.tsx`、`toolKnowledge.ts`、`equipmentProfiles.ts`。前者仅控制展示/选择，不另加工具性能权威；后者仍唯一数值来源。
- **验收：** 未选不隐式决定工具；选 A→进场的 selectedToolId=A，选 B→B；离开后进入别的工作不意外保留不兼容工具；计划顺序变化不扣“错误顺序”。

### F03 安全与操作前检查：专业判断的底线

- **真实任务：** 草坪的石头阻挡会被相应刀具抛射/撞击风险；绿篱的硬木需要不同处理。保留局部限制而不是全院上锁。确保危险提示出现在**实际操作附近**，而不是几秒后某一层 toast 里。
- **工具状态：** 0 电/卡住/损坏应在操作前明显可见，按现在的 `ToolUseGuard` / `durabilityRules` 保证真实禁止动作；Recharge、Clear Jam、Repair 有不同语义（不因充电修复损坏）。不要让玩家误以为充电就等于维护完成。
- **额外现实安全注意：** 涉及刀片保养/移除卡枝时，现实需断电/停机并遵循制造商安全程序；若没有真实实现该流程，游戏只做简单提示，不提供不完整的现实操作指导。修篱前有活动鸟巢时应避开扰动；**本轮不得仅为增加知识而凭空加入鸟巢硬锁/生态季节模型**，可在知识卡/未来内容处如实提及。
- **代码定位：** `HazardTaskStage.tsx`、`gardenFixtures` / `fixtures.ts`、`gameStore` 各动作、`toolUseGuard.ts`、`durabilityRules.ts`。
- **验收：** 被安全约束阻断时**不改变目标、不扣有效工作投入、不产假碎屑、不伪成功**；恢复后仍能继续原工作，已有进度保持。

### F04 割草：草坪覆盖、推行方向、电量和保护花坛

- **玩家学到：** 手推滚刀与电动机的工作范围/操作方向有差异；宽机器在开放地带更快，但靠近花坛要留意精度；电量耗尽不能再切，补充后继续原状态。
- **真正操作：** 保留 `LawnTaskStage.tsx` 路径采样、`MowerTool.tsx` 轮/刀动画、P0 `WorkCell` 唯一割草状态；要求路径绘制、结果高度/颜色、工具动画和电量状态彼此一致。手推滚刀倒退不应无意间和向前等效。不要用键鼠一次瞬移强制割完整块草。
- **工程检查：** `pathLength(samples)` 是否含 drag 前一段？同一实际世界路径按 2/8/32 个采样点及按 1/5/20 次 pointerMove 分割，最终覆盖、电量、记账是否等价（明确容忍误差）；`clampPointerStep` 不应静默丢掉剩余输入距离导致快速移动少割。防拖动穿过不可达区域；无电后动画和结果停止。
- **视觉：** 将方块草格的“切前/切后”可辨性作为目标。优先重用现有 grass textures/GLB 或轻量 instancing；不增第二套 cut flags，不拷贝 Grass Blade 仅参考技术代码，不为了视觉引入大材质系统。观察过度 grid 化是否让初学者误解为马赛克。
- **现实知识边界：** 草坪剪去不超过约三分之一叶片是常见园艺养护建议，但当前游戏没有高度档位与真实长势时，**只可作为明确标注的背景知识**，不得写成已经模拟的机制或强制罚分。
- **验收：** 手/电两工具通过可视范围与能量结果区分；电量 0 阻断；快速与慢速拖动覆盖同一路径的一致性有可执行断言；误伤仅一次且可在 Review 中解释；返回总览后同一草坪状态保持。

### F05 绿篱：精修、大范围、局部安全与掉落物

- **玩家学到：** 手剪适合小范围的精细修整；动力剪适合较长面但受电量/硬木/过剪约束。不要将手剪直接解释为可以处理所有粗枝；不要把任何“快速”都等同于“更专业”。
- **行为：** 选择工具 → 在绿篱真实位置做差异化扫过 → cluster 边界/过切结果可辨 → 每个有效切割只产生一次落地剪枝。危险物就在同一地理位置，检查后可移除；后续耙/吹/袋可继续处理碎屑。
- **代码定位：** `HedgeTaskStage.tsx`、`GardenWorldOverlays.tsx`、`gameStore.cutHedgeCluster`、`garden/reducer.ts`、`gardenPlacement.ts`、`GardenToolView.tsx`。
- **验收：** 同一已剪 cluster 不重复生成 debris；已剪后过切留下可辨缺口/质量损失；动力设备 0 电/卡住不会产生假工作；碎屑落在用户真实能清理的地面，而非物体背面或镜头外。

### F06 修边：大面积与边缘任务必须独立

- **玩家学到：** “草坪割完了”不等于“路径边缘修好了”；独立的半月形手动修边器与线割机作用方式不同。优先画面能让玩家看出**为什么需要第二件工具**。
- **行为：** 仅在路径—草坪界面附近形成有效修边；独立 edgeSegments 持久化；裁剪宽度和效率受工具选择影响。保留现有程序化手动修边器轮廓，不伪装为线割机；如未来替换 GLB，先核实许可与身份。
- **代码定位：** `src/game/garden/edgeFixtures.ts`、`EdgeTaskStage.tsx`、`gameStore.applyEdgeWork`、`reviewSelectors.ts`、`GardenWorldOverlays.tsx`。
- **验收：** 只割草时 edge=0/未完成；只修边不增加 lawnPct；切到不同工具有差别且电量约束正确；视觉边缘变齐；离开返回仍保持。

### F07 花坛：杂草 vs 观赏花，切顶 vs 拔根

- **玩家学到：** 识别目标，线割仅能处理地上部分，手动除草/拔根才能去除这批任务的目标根系；误把花当草会产生不可逆损伤（仅本次游玩内）。不必引入长期植物生长模型来冒充“复发已验证”。
- **行为：** 花与杂草的形态在场景中确有区分（不能只通过文字和球颜色猜）；线割后地上部缩短，根仍显示在状态/现场提示；手动除草后根移除，杂草实体消失或留可收集残余；误伤花仍可见。
- **代码定位：** `FlowerbedTaskStage.tsx`、`garden/fixtures.ts` 中 completion flags、`garden/reducer.ts`、`gameStore.pullWeed/topCutWeed/damageFlower`、`GardenToolView.tsx`。
- **验收：** 每个需要完成的杂草必须在可见且可交互的任务范围内；无电线割不成功；错误工具不暗自执行拔根；重复点击不重复损伤；花与杂草可辨；存档刷新结果一致。

### F08 地面清理：耙/吹/袋与真实返工

- **玩家学到：** 耙用于集中，吹用于有方向地转移，装袋只移走已聚集的材料；清理顺序可节约一次重复劳动，但真实庭院中也可选择覆盖/堆肥，**游戏中规定的装袋任务不等于现实唯一正确方法**。
- **行为：** 散叶/落枝/拔草残余来自相同世界状态；远处碎屑不能瞬间全院装袋；物体可以从西南/东侧通过点击聚焦进入清理；重叠脚印按事件顺序认定先清、再脏、确实再清。
- **代码定位：** `DebrisTaskStage.tsx`、`GardenWorldOverlays.tsx`、`gameStore.rakeDebris/blowDebris/bagNearbyPiles`、`garden/spatialRework.ts`、`garden/reducer.ts`。
- **验收：** A=先修篱后清、B=先清东侧后修篱再清：同样最终质量下 B 的真实 rework > A；西南清扫→东侧剪篱不能算重清；仅再次出现枝叶但尚未清理只算 potentialRedirty；物件事件具有唯一 ID、不重复丢失。

### F09 Review、Finish 与重试：把行为变成经验，不变成成绩骗局

- **内容顺序：** (a) 本次完成了多少工作，质量/安全怎样；(b) 哪些工具产生了哪些结果；(c) 哪个事件造成风险或返工；(d) 可以尝试的**一个或两个情境化改进**；(e) 同条件第二轮比较（只在最终质量相近时讨论效率）。
- **Finish 的语义：** 一个明确的“本次结账/封存”。冻结一个 `VisitSummary`。封存后不能一边修改庭院一边显示旧的封存数据：优先让世界只读、可观看；提供明确“相同条件再试一次”入口。若希望重新打开同一轮，要显式另建修订记录，不静默改历史。
- **比较：** 结果先检查 `fixtureVersion`、安全、观赏植物损伤、任务覆盖、剩余碎屑；不满足可比性时解释“质量不同，不能只凭投入比较优劣”；相似质量时展示**差在哪一项动作、返工哪里减少、选了哪件工具**，引用可用 event id。避免把基于常数的游戏 effort 说成真实分钟或真实专业效率。
- **测试：** 连续 Finish 多次不得生成多条相同封存；封存后更多操作不改变任何封存 summary 或实际世界；刷新后两轮数据稳定；第三次、第四次不会覆盖第一二次而不告知；若有历史 cap，在 UI 说明保留最近 N 次。
- **代码定位：** `gameStore.finishVisit`、其他全部 mutating actions 的封存守卫、`visitSummary.ts`、`learningAdvice.ts`、`reviewSelectors.ts`、`WorkReviewPanel.tsx`、`GardenShell.tsx`、`migrateGarden.ts`。
- **验收：** 新玩家可实际完成两轮，看到不同决策的事件依据和可比性限制；没有硬编码某个固定工序分数；可导出/截图对照不强制新增后端。

## 3. 围绕“会判断”的教学交互：一个最小、完整的学习回路

### 3.1 设计方式：现场条件 → 选择 → 操作 → 观察 → 自我归因

例一（草坪）：玩家发现开阔草坪与邻近花坛。选宽机器时覆盖快、精度有限，可能需要保留边缘给别的工具；选择手推设备则窄、工作较慢。Review 用同一庭院真实动作说明不同，而不是显示“动力机高级”。

例二（除草）：玩家先选线割，能看到植物变矮但仍标为根未移除；换手除草器才能完成根部处理。教的是目标与工具机制匹配，不是“永远只能用手”。

例三（工序）：玩家先把东侧落叶清掉，再修绿篱掉下碎屑；必须再清一次才算 spent rework。第二轮改顺序但保持相近质量，Review 才能对投入进行合理比较。

### 3.2 教学出现位置与信息密度

- **操作前：** 一句现场事实 + 可选的两件工具的简短区别 + 一句安全/准备提醒。避免超过一个小卡片，不要强制看整页说明或答题。
- **操作中：** 只在行为有意义时反馈，比如“电池耗尽”“仅切除顶部”“新枝叶落在刚清好的地上”；错误工具即时告知原因，不刷屏。
- **操作后：** 可见状态优先于 toast。第一次有效操作可出现一条简短“你刚才观察到了什么”的非阻断提示，用户可关闭。
- **复盘：** 基于真实事件 ID、覆盖率与后果；默认先解释最影响质量/安全/返工的 1–3 项，其他信息折叠。
- **第二轮：** 不重复全套 onboarding，不强制按“推荐”做；帮助玩家换一种合理路线进行**可比的**工作。

### 3.3 决策证据的数据约束

不要加入复杂的“猜答案系统”。先尝试通过现有 `GardenEvent`, `WorkSnapshot` 与 `toolKnowledge` 推导：当时选了什么工具、哪片区域、实际切到什么、后来产生什么变化。仅当这个推导不够、且确实直接提升解释质量时，添加极薄的 `decisionContext` 或 `actionEvidence` 字段。**不允许**另建一个与 GardenDomain 并行的工具/草坪权威存储。

建议 `LearningMoment`（**仅派生 UI 示例，不是强制新表**）：

```ts
interface LearningMoment {
  sourceEventIds: string[];     // must resolve to real events or known WorkSnapshot action refs
  areaId: string;
  toolId?: string;
  observedResult: string;      // what actually happened
  whyItMatters: string;        // scenario-specific explanation, not fabricated causal proof
  alternative?: string;        // qualified option, never one forced order
}
```

若由 `lawnSweep` 来的动作没有稳定 event ID，需先决定最少量的可追踪补充记录；不能只给 UI 生成一个“看起来合法”的 event id。对同一动作避免重复记账/重复生成教育事件。

## 4. 工具—场景—可见因果矩阵（产品契约）

| 主要对照 | 玩家看到的初始问题 | 正确可用的工具机制（情境依赖） | 玩家必须亲眼看到的差异 | 不允许的捷径 |
|---|---|---|---|---|
| 滚刀割草机 vs 电动割草机 | 大草坪 + 花坛边 | 手推前进窄割幅；动力宽割幅耗电 | 轨迹宽度、方向、资源变化、误伤 | 两个按钮都直接完成草坪 |
| 普通割草 vs 修边 | 沿路径草坪 | 大机切平面；手动修边/线割处理界面 | lawn% 和 edge% 独立，边缘确实变齐 | 一次割草自动算修边 |
| 手动绿篱剪 vs 电剪 | 东侧长绿篱 + 局部硬木 | 窄精修 vs 较宽快修，限制不同 | 外形、切除带、碎屑、过剪 | 无电仍可以工作、粗枝软剪随意切 |
| 线割机 vs 手除草器 | 花坛杂草 + 观赏花 | 切顶 vs 物理去根 | 地上部分变短 / 根保留、真正去根、误伤 | 线割直接“完成拔根” |
| 耙 vs 吹叶机 | 散落叶/剪枝 | 控制地堆积 vs 推向目标方向 | 堆积地点、吹散风险、动力消耗 | 吹叶即凭空删除落叶 |
| 聚堆 vs 装袋 | 地上已有堆 | 收集成堆 vs 搬离/装袋 | pile state transition、局部距离 | 点击任意空地全院清除 |
| 先清后剪 vs 先剪后清 | 东侧叶片和可修绿篱 | 各自合法，顺序关系决定是否重清 | 第二次实际清扫、相同质量下不同投入 | 仅凭选择计划顺序加罚 |

**工具知识应与可体验的规则一致。** 若某知识说明现实中存在、但当前操作无法表现，标注“现实补充知识 / 尚未模拟”，不借此给玩家暗扣质量分。

## 5. 专业园艺事实核验与游戏简化边界

以下为本轮检查过的外部专业资料，用于校正**教学措辞与安全常识**，不是要求复制百科或增加复杂物理系统。Cursor 如继续扩充园艺指导，必须核验适用场景，保留来源 URL 和 `VERIFIED_SOURCE` / `SIMULATED_MODEL` / `NOT_SIMULATED` 区分。

| 真实原则 | 可信来源 | 游戏可教的部分 | 不应声称的部分 |
|---|---|---|---|
| 割草前检查石头等可被刀具抛出的障碍物；维护前停机/切断动力 | Canadian Centre for Occupational Health and Safety, [Rotary Lawn Mowers](https://www.ccohs.ca/oshanswers/safety_haz/landscaping/rotary.html) | 草坪局部危险物检查、清除与阻断 | 实际机具的完整安全操作认证 |
| 常规养护通常建议一次剪去不超过约三分之一草叶高度；剪下草屑通常可留在草坪 | University of Minnesota Extension, [Mowing practices for healthy lawns](https://extension.umn.edu/garden-and-home/yard-and-garden/lawns-and-landscapes-in-minnesota/mowing-practices-for-healthy-lawns) | 解释“覆盖/高度与草坪健康不同”；不强迫所有草屑装袋 | 游戏没模拟剪切高度时假装有草坪生理反应 |
| 修篱前检查活动鸟巢，避免不当扰动 | Royal Horticultural Society, [How to Trim a Hedge](https://www.rhs.org.uk/plants/types/hedges/how-to-trim-a-hedge) | 作为 preflight 补充提醒，强调观察周围环境 | 没有鸟巢对象却声称已经完成鸟巢检查，或把英国法规无条件当作美国当地法律 |
| 手拔/挖根可针对杂草根结构，线割/割草更多属于控制地上部分 | University of Maryland Extension, [Manage Weeds Without Chemicals](https://extension.umd.edu/resource/manage-weeds-without-chemicals-maryland) | 线割切顶不等于移根，情境化工具选择 | 保证任何品种一次拔根绝不复发 |
| 不必一律装袋处理落叶；草坪叶片覆盖、花坛利用、堆肥也可合理采用 | University of Minnesota Extension, [Leave the leaves? A smarter approach to fall cleanup](https://extension.umn.edu/leave-the-leaves-a-smarter-approach-to-fall-cleanup) | 解释“当前场景的任务要求收集”，不是普适标准 | 给现实所有落叶清扫都判定为正确做法 |

**严谨边界：** 正确性的关键是玩家能把工具用途迁移到现实中的判断，不是照着游戏拖动鼠标来真的操纵危险刀具。涉及任何危险设备维护，只提示“停机、查阅制造商说明并按安全规定操作”，不详细模拟会误导的带电排障步骤。

## 6. 工程执行路线：**一轮连续推进，七段闭环，不分小任务来回汇报**

下列 `Wave` 是 Cursor 的内部实施序列。**用户最终一次收到完整可试玩交付**；每段自行跑关口并 commit，自动继续。若某问题阻断主线，则局部修好后继续原路线；不因视觉反复调光停几小时。主文件不变化成另一个 V07 产品目的。

### Wave 0 — 起点保护、可跑环境与测试基准

1. 确认 `feature/v06-professional-learning-loop` HEAD = `d8eb23c` 或更新的兼容提交；检查本地 WIP，不覆盖用户文件；建立新 feature 分支。记录 `git status -sb`、remote SHA。
2. 确认本地 `npm ci`（如已有锁定依赖无需重复安装）及 `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build` 可执行；保留现有 112 测试不删除。
3. 准备**可重复的本地试玩入口**：`npm run dev` 或生产构建本地 `npm run start`，记录访问 URL/端口、测试浏览器、操作系统、最初版本 fixture。禁止声称本地访问路径可由用户互联网打开。
4. 非破坏性测试数据：对现有存档使用**隔离的浏览器 profile/context**或只在显式 Debug/QA 模式加载确定性 fixture；默认不得 `localStorage.clear()` 或 `startV03Garden()` 自动覆盖真实用户存档。QA fixture 使用 stable seed/version、恢复/重置路径、有回退方法。
5. 建立一个小的 `docs/V06_OWNER_PLAYTEST.md`（**试玩说明而非第二份 Master Spec**）与 `docs/v06-evidence/`，随持续开发更新，不只最后补图。
6. **关口：** 旧测试不回退、可打开首页、可按操作进入一个任务、无白屏；立即进入 Wave 1。

### Wave 1 — 现场观察与选择是可玩的，不是被 UI 替代

1. 复核 F01/F02/F03 真实体验。缺省首屏能看懂花园任务；Inspect 必须给具体新信息，不强制锁全部工作，保持自由顺序。
2. `WorkConfirm` 工具选择需明确而非默认首项后不经意按 Start。可以初次未选禁用开始或加入“使用推荐值”显式动作；重复同类任务记住用户最后选择但注明。兼顾 5–8 分钟试玩流畅性。
3. 用 `toolKnowledge` + `equipmentProfiles` 生成轻量同场景工具对比和前置风险，避免“绝对最佳”。**不要通过改工具说明改变其真实能力**。
4. Work plan 可选、可调整，可不按计划操作；反馈“你实际选择”而非强制结算唯一顺序。
5. 明确封存/未封存状态在主界面的可见语义，为 Wave 4 的 Finish 行为打底。
6. **关口：** 玩家能从进入到开始施工不读长文；新玩家必须至少作一次明确工具选择；Inspect 有可观察状态变化；两个不同合法工具均能进入对应任务，自动测试与真实浏览器核实。

### Wave 2 — 操作因果与工具真实差异（保持同一庭院）

1. 根据本文件 F04–F08 和工具矩阵，集中校准当前操作。先修有误导教育意义的差异：切顶/去根、宽草坪/窄边缘、剪篱/落屑/清理、手/电容量。
2. 修 `lawnSweep` 输入/路径切割的多采样分段一致性；**不得重建权威草坪状态**。保留真实鼠标/触控操作；明确当鼠标移出 canvas、pointercancel、OrbitControls 拖动竞争时会怎样，避免拖动卡死。
3. `ToolUseGuard` 真正通过 store 执行所有相应动作；操作不合法不改 world 和“有效劳动”记录。重点确认 `pullWeed/topCutWeed` 选择工具正确，不能因为 UI 绕过另一个底层路径。
4. 绿篱剪下的枝叶、花坛拔草材料、初始落叶用同一世界持久数据投影；空间能被相应清理工具触达；`gather/bag` 只对实际目标生效。
5. 修所有会让玩家误以为工具“已经工作”的动画/状态矛盾；不需要真实刀具碰撞或全物理叶片。
6. **关口：** 完整三条路径（一条草坪、一条除草、一条修篱→清理）实机可操作，UI/状态/事件一致；路径采样与工具差异测试绿；进入 Wave 3。

### Wave 3 — 行动证据、准确复盘与学习迁移

1. `VisitSummary` 只封存真实事件、工具与最终世界快照，维护 schema migrate 与历史 cap。对每条教育建议实现 `sourceEventIds` 可解析或准确标注为**通用提示**；不得虚构发生过的失误。
2. 标准化努力单位：只有真实成功/有投入的动作记 productive，已返工才记 rework，无法操作的失败可记 ineffective（但不得扣成实做）； setup/recovery/charging 一律用模型值。防止不同工具路径分段数造成“越慢拖越低效”的假结论。
3. 完整完成度：草坪、edge、绿篱、要拔根的杂草、留存碎屑、风险/损伤；无未完成但 `acceptable` 的虚假认证。安全/损伤先于速度比较。
4. Finish 后封存与工作状态一致：不允许暗中再施工改变本次记录；多次 Finish 幂等，明确重新尝试。
5. 二次尝试：完整复制**相同初始 fixture**，但不复制上轮已被剪过的状态；上一轮历史不能丢，第二轮与第一轮同质量条件下，指出有证据的具体行为差别。不可比时解释原因，不给未经证明的“你更专业了”。
6. **关口：** A/B 不同顺序的事件依据可复现，封存/迁移/重试不损坏历史；必须至少一组**不同工序、同质量、不同返工**的可执行自动化测试。

### Wave 4 — 只做服务于理解的视觉和交互可读性

1. 优先解决结果不直观的问题：割草立方网格过强、花卉/碎屑球体难辨、绿篱已修与未修不够明显、任务热点偶发难点、debris 镜头偏 patio、危险物方块/石块不自然。
2. 以已入仓 CC0 `public/assets/models/yardshift-kit/` 和现有 grass textures 为默认资源；已有手动修边/手除草器独立 silhouette 是**正确的**，可局部改善，不要又用不匹配的 kit GLB 替代。
3. 对所有模型使用**真实模型负责外观，透明可点击 proxy 负责可靠操作**；改模型不能改变任务对象 ID/碰撞权威。剪篱、碎屑、花坛的跨区域回到总览应保持同一世界结果。
4. 性能优先：测试典型桌面大小、浏览器窗口缩放及窄屏。控制 draw calls、透明层遮挡、工具 GLB 重复加载、grass instancing。FPS 用浏览器真实测量并说明机器/分辨率/采样方式；无法测就 `NOT_MEASURED`，不要臆造 60FPS。
5. 最多做**一轮核心可辨性改善**，经过真实试玩后若仍需大改，记录为产品负责人待评估，不无止境改 Shader、阴影、动画。
6. **关口：** 用户能看到操作前后的实体区别，工具和效果对应，浏览器里热点可靠；性能没有明显回退；下一步完成整体验收。

### Wave 5 — 自动化、浏览器与人类可试玩交付的一体化 QA

1. 强化本文件第 7 节测试矩阵，修复已有弱断言（如 J16/J17 仅 `>=0`）；不要单纯把测试数从 112 堆到 200，而忽略一整条玩家操作链。
2. 使用确定性 fixture 做**至少两条完整端到端路线**：A 先剪后清；B 东侧先清后剪再清（同质量/同范围下 B 有实际重清投入）。路径截图/短录屏可作为辅助证据，但断言必须来自真实状态。
3. 真实浏览器里至少操作一次剪篱、耙、装袋、线割/手除草、割草、修边、Finish、再试；检查鼠标拖动与取消、相机、无错误、持久化；**不能以直接调用 `window.__yardshift` 代替浏览器交互作为 UI 通过证据**。调试直调仅用于确定性数据准备/客观单测，不算端到端点击。
4. 写可供负责人不看代码照做的 5–8 分钟试用指引、观察题、BUG 复现路径、结果填写表；这就是我们以后每轮交付都可以实际测试的资产。
5. 跑 `npm run typecheck && npm run lint && npm run test && npm run build`，记录真实数字/错误；最终存档迁移回归、工具运行可恢复、历史正确、Git 状态清楚。
6. 准备**本地预览方法**（命令/端口/如何恢复先前试玩进度/如何启动隔离测试）；不部署。如果需要更易访问的在线预览，必须等待用户明确授权，不能在未授权下发布。
7. 每个 wave commit，完成后 push feature；更新原 `docs/V06_EXECUTION_LOG.md` 和 `docs/ASSET_MANIFEST.md`，并提供真正的截图、测试报告、已确认局限。
8. **关口：** 用户可以独立打开本地试玩版、按说明跑完整体验和 A/B，任何客观阻断错误已修；未实际做人类试玩则如实 `HUMAN_REVIEW=NOT_TESTED`，不能标完全教育验收通过。

## 7. 可靠测试矩阵：不以测试数量替代测试质量

**强制格式：** 每个场景有 `initial fixture + user/action input + expected world/action/visit state + negative assertion + evidence type`。复用已有 tests，增强薄弱部分；仅增加真实覆盖缺口。脚本运行真实失败时不可擅自缩弱断言来变绿。

| 编号 | 真实验证目标 | 可复现输入/路径 | 必须断言（不是能跑/不报错） |
|---|---|---|---|
| Q01 | 老存档兼容 | 用 v03、v06.1、v06.2 数据迁移 | 已割格/原植物/工具状态不丢、visitHistory 正确初始化 |
| Q02 | 首次未选择工具 | 打开一项双工具工作，未作明确选择 | 不悄然自动按第一件开工；有清楚的可选动作 |
| Q03 | 选择持久语义 | 选择 shears，切到 trimmer，再返工 | 当前工具与作业记录一致、非兼容工具不能执行 |
| Q04 | Inspect 增量知识 | 进入→Inspect 一次→再次 Inspect | 真实展示新发现，第二次不重复扣 setup |
| Q05 | 局部危险阻断 | 石头未移除，在该范围割草 | 目标未被切、无假进度/误生成资源、清除后可继续 |
| Q06 | 不危险区域自由施工 | 留一块危险没清，另一处工作 | 非危险区允许正常施工，不全院锁死 |
| Q07 | 电池耗尽恢复 | 动力机电量=0→操作→Recharge→继续 | 电量 0 不切，充电不恢复 broken/jammed，原进度保留 |
| Q08 | 手动/动力割幅 | 同等真实路径切同片草 | 覆盖宽度区分；量化功率/覆盖差，不依赖工具文案 |
| Q09 | 割草方向性 | 手推滚刀向前/倒退等长 | 结果差异符合规则，后退不能等效向前 |
| Q10 | 采样频率不敏感 | 2/8/32 samples 同真实路线 | 覆盖与资源/effort 差在声明容差，不按事件频率双耗电 |
| Q11 | pointer move 分段 | 同路线 1/5/20 次 move + 快速拖动 | 路径未静默被截断、额外碎屑/工时不重复 |
| Q12 | 持久草坪状态 | 割半块→离开→刷新 | grass cells 与表现仍保留，旧迁移不抹掉 |
| Q13 | 草坪/修边独立 | 只割草／只修边 | lawnPct 与 edgePct 分别变化，不互相冒充 |
| Q14 | 动力/手动修边限制 | 不同工具沿真实 edge | 能耗/范围正确；脱离边缘无有效进度 |
| Q15 | 动力绿篱剪安全 | 硬木未清 + 0 电分别测试 | 不切、不生成碎屑，合法恢复后可继续 |
| Q16 | 绿篱一次剪枝 | 同一 cluster 两次触发 | 剪枝实体恰一份、来源事件可追踪、过切单独记录 |
| Q17 | 线割切顶 | 对可操作杂草使用 string-trimmer | `topCut=true`、`rootRemoved=false`、视觉变短 |
| Q18 | 手动拔根 | 先 top-cut 再用 weeder | `rootRemoved=true`、目标完成、废料可继续清理 |
| Q19 | 错误工具及无电 | 花坛使用不适配工具/线割 0 电 | 原状态不改变，清晰错误反馈，没有有效劳动记账 |
| Q20 | 花卉保护 | 错拔观赏花两次 | 花卉损伤可见且最多记一次，质量不能虚假达 acceptable |
| Q21 | 耙/吹/袋差异 | SW + east 刚入场、同一区域操作 | 耙聚堆、吹定向移动、bag 局部收集；远处不消失 |
| Q22 | 空间误判保护 | 只清西南，再剪东侧 | `rework=0`，不是因为顺序本身判罚 |
| Q23 | 同区域真实重清 | 先清东→剪东→再次清东 | 第二次实际清才 `spent rework > 0` |
| Q24 | 潜在返工 | 先清东→剪东但尚未再次清 | `potentialRedirty>0`、`spent rework=0` |
| Q25 | 真实事件关联 | 触发切顶/误伤/返工 | advice/visit sourceEventIds 指向有效事件，没做事不编造 |
| Q26 | 有效 work effort | 只成功工作一次、同动作重试无效 | productive 只对有效工作增加；无效/准备/恢复分类正确 |
| Q27 | Review 诚实质量 | 空庭院直接 Finish，或有花卉损伤 | 不宣称 acceptable；区分 incomplete 与 needs attention |
| Q28 | Finish 幂等/冻结 | Finish 两次→尝试继续切/拔/充 | visitHistory 只增一次；封存摘要与 world 一致，禁止静默改封存态 |
| Q29 | 同条件重试 | Finish→retry→重新做另一顺序 | 新 world 恢复相同 fixture，历史保留且不污染本次世界 |
| Q30 | A/B 公平比较 | 同 fixture 同质量两轮，一轮重复清 | 只在可比条件下报告 effort 差，实际重清为主因 |
| Q31 | A/B 不可比 | 同 fixture 不同安全/花卉损伤/覆盖 | `comparable=false`，解释质量优先、不给效率胜负 |
| Q32 | 多轮历史与版本 | 3 次/10 次 visit + migrations | 正确保留/限制 N、无重 ID/跨版本误比较 |
| Q33 | UI 操作真实性 | 浏览器点击真实工具、拖动、Finish | 世界动作确实变化；不能只靠 store 直调算通过 |
| Q34 | 窄屏/键鼠/触屏 | 典型 desktop+窄屏；pointercancel | 可操作、不被弹窗遮盖、拖动释放、不误伤 |
| Q35 | 外观与权威统一 | 切/拔/清后进入总览再回来 | 3D 实体对应同一权威状态，未复活、未重复 |
| Q36 | 性能与资源 | 同浏览器首次/多次进场 + 操作 | 无明显加载泄漏；报告有依据的 FPS/内存，不能臆测 |

**特别点名弱断言：** `judgmentLearning.test.ts` 当前 J16/17 末尾 `expect(rework).toBeGreaterThanOrEqual(0)`，无法证明 rework 真正发生；应以可控重清路径和确定性坐标/事件改成严格 `>0`，并有对照为 `===0`。同样不允许 `expect(potential>=0)` 之类伪证据作为 PASS。对于需要从 UI 触发才能成立的判断，必须有真实浏览器交互证据。

### 每个 Wave 都要跑什么，而不是只在最终检查

- **每次代码段完成：** 相关针对性单测 + typecheck（很快发现接口错位），提交到本轮 feature。
- **每个 Wave 关口：** 全量 `npm run test` + `npm run typecheck` + `npm run lint`；任何红色必须说明并修复回归，不通过就不能标 DONE。`npm run build` 至少 Wave 0 基线、Wave 3 数据封存后、Wave 5 最终运行。
- **有玩家交互变化的 Wave 1/2/4/5：** 使用同一真实浏览器入口跑 1–3 条动作，按 `ACTION→WORLD CHANGE→REVIEW` 记录，不为了凑数量重复截图。
- **最终：** 覆盖 F01–F09、A/B 比较和保存恢复；测试通过数字为真实运行结果，报告新加/强化的测试和剩余已知盲点。

## 8. 负责人每轮都能直接试玩：交付必须包含一个真实可复现测试包

**这是本轮最高新增要求之一。** 今后每轮无论功能规模，不能只有 SHA、测试数量和截图，必须交付**人类从入口到结论的试玩方法**。不依赖 Cursor 在一旁解释操作，不要求用户自己打开 Developer Tools。

### 8.1 本地启动与进入

- README/`docs/V06_OWNER_PLAYTEST.md` 写具体：`git fetch` / checkout 对应 branch；项目所在位置；`npm ci` 条件；`npm run dev` 或 `npm run build && npm run start`；浏览器打开 `http://localhost:3000`（只有服务器真实监听 3000 才写这个地址）。记录是否需要相同机器。
- **正式/测试存档隔离：** 推荐使用新的浏览器 profile 或临时专用测试环境。提供 UI 中“仅重置此试玩庭院”路径，说明会影响此 profile 的哪个存档。默认不得清全站 localStorage；不要把用户之前的 `yardshift-v03` 直接擦掉。
- **确定性重开：** 若是刚开始的测试 profile，可用 Start fresh 或 Retry same conditions；已有存档用户先备份/导出（若没实现导出，可至少明确备份与风险）。不要承诺存档完全安全而没有对应回归测试。
- 如当前没有自动公开 URL，不得说“点击线上链接试玩”；未授权部署就以本地可重复运行方式交付。

### 8.2 负责人 5–8 分钟主试玩脚本（非强制正确路线）

**第一遍：探索 + 工具差异**

| 预计步骤 | 负责人操作 | 应看到的变化 | 一旦失败如何记录 |
|---|---|---|---|
| 0:00–0:45 | 打开庭院，不看说明找一个可做的工作；按 Inspect | 能找对入口，检查提供真实额外信息 | 记“没看到入口/检查无意义”的画面与点击位置 |
| 0:45–1:30 | 进绿篱，选择手剪或动力剪，剪一小段 | 工具有真实不同形状；绿篱变化、地上有枝叶 | 记录具体 cluster、工具、电量与是否落屑 |
| 1:30–2:15 | 去东侧清理，用耙、袋；可尝试吹叶机 | 耙聚堆、袋收走；不能隔空装袋 | 记录堆位置与是否能被相机/鼠标操作 |
| 2:15–3:10 | 选择割草机，拖动一段草坪，观察精度和电量 | 草随路径变化，可回总览保留 | 记录是否因拖动跳帧/看不懂草变化 |
| 3:10–4:00 | 沿小路修边，检查 Lawn 与 Edge % | 两者互不混同，边缘可见改善 | 记录工具、进度和能否点到 strip |
| 4:00–5:00 | 花坛先线割一棵杂草再用手除草器；避开花 | 先切顶留根，后拔根，花和杂草分得清 | 记录误选时反馈及是否卡死 |
| 5:00–5:45 | Finish → Work Review | 实际完成度、质量、证据型建议，无假“专业完成” | 记录 advice event 是否对应真实动作 |
| 5:45–8:00 | Try again（同院），换一种工序/工具，二次 Finish | 相同初始环境；可比质量则比投入，不可比则说明 | 记哪里比较符合/不符合真实经历 |

**第二条专门的可比 A/B 测试路线（Cursor 自动化应能演示，负责人可选做）：** A 先剪东侧绿篱→耙堆/装袋；B 先清东侧初始落叶→剪同绿篱→再清新枝叶。两轮做**同样数量、同样质量**的必要工作才能谈效率；如果负责人没时间两轮做完整草坪，可用隔离 fixture 的短路径验证“空间返工”而不称为整场效率测试。

### 8.3 四个不诱导答案的人工验证问题

试玩前**不要**把右边答案展示给参与者，避免背诵系统文案。试玩后问：

1. 如果这块草坪旁边紧靠花坛，你为什么选刚才那台割草机？在什么情况下会换另一台？
2. 线割过一棵杂草后，为什么它可能还不算被清除？你会怎样处理？
3. 你有没有做过两次相同区域的清理？是什么后续工作造成的？
4. 如果同样庭院再做一次，你会先检查什么、如何安排工具或顺序？理由是什么？

**记录而不是打分作弊**：对每题 0/1/2：0=不能说明/明显错误；1=部分正确但需要诱导；2=能根据自己真实操作独立解释。四题总分满分 8，仅作内部诊断，不声称具有经验证的教育测量效度。建议标记 `Observed / Needs iteration / Not tested`。没实际人类回答，全部 `NOT_TESTED`，不得由模型代填。

### 8.4 最低可交付测试包

`docs/V06_OWNER_PLAYTEST.md` 至少包含：确切分支/SHA、本地启动命令、访问地址及前提、如何隔离旧存档、两条操作路线、每步预期状态、填写异常的模板、4 个理解问题、已知 limitations、反馈联系人（不填私人邮箱）。可以附小样本测试结果，但只能写真实观察结果。

截图建议 6–8 张有证明价值的代表性场景：首屏、工具选择对比、真实 cut path、剪枝落屑、先切顶留根、重清、封存/同质量 A/B、移动端或小屏（如真测）。数量不是验收目标；不要求为截图重复操作 50 遍。

## 9. 客观测试 vs 产品判断：职责分工与停止条件

| 类型 | Cursor 必须做 | 负责人判断 | 不得冒充 |
|---|---|---|---|
| 工程正确性 | 编译、类型、事件幂等、路径、持久化、Guard、历史可比性 | 可复核结果 | 截图替代状态测试 |
| 浏览器可靠性 | 真实点击、拖动、取消、镜头、错误、UI 状态 | 是否容易上手 | 仅调用 Zustand store 说“已通过 UI” |
| 工具学习价值 | 提供前因后果与真实知识来源 | 是否理解、能举例、愿意再试 | 自动化代人评判“已学会” |
| 视觉理解 | 工具/效果真实对应、无重大遮挡 | 喜欢与否、是否自然 | 为追高帧/写实无限修改 |
| 发布准备 | 提交完整可运行 feature 与本地试玩路径 | 决定是否公开部署 | 未经授权擅自部署或合并 |

**立即阻断并修复的情况：** 操作不改变真实世界、错误工具可绕过、安全约束无效、Finish 后历史不一致、刷新丢存档、同区域返工无法复现、任务不可达、无法本地运行、授权不明确却导入。

**达到便继续的情况：** 草地不像摄影作品但能清楚看出割前割后、工具轮廓不是高保真却准确表达用途、音效缺失、危险石块是合法代理但安全含义明确。这些进入 Backlog，不应拖住完整体验交付。
